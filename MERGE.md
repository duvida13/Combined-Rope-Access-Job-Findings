# Manual incremental merge procedure

Use this procedure whenever the user asks for combined findings again. **Do not repeat the initial historical extraction.** The initial snapshot covered the four sources through 29 September 2026.

1. Read [`state/source-checkpoints.json`](state/source-checkpoints.json). The four commit SHAs are the last successfully merged source revisions. Read the existing [`state/observations.csv`](state/observations.csv), [`vacancies.csv`](vacancies.csv), and [`review-links.csv`](review-links.csv) as the cumulative baseline.
2. Fetch the current default branch of each source repository. For each, compare its saved SHA to current HEAD with `git diff --name-status OLD_SHA..NEW_SHA`. Inspect **only added or modified published job files**: `digests/` and `seen-jobs.md` for ChatGPT (the repository changed from its former `daily/` and `data/job-index.md` layout in October 2026); `digests/` for Claude; `finds/` for the two Grok repositories. Ignore candidate notes, private context, migration-only copies of already-merged dated files, and Claude's `state/seen_jobs.json` (it includes rejected hits). If a source SHA is unchanged, skip that source entirely.
3. Extract only position title, country when present, vacancy URL, source agent/file, source status, and source date. For a changed cumulative ChatGPT index, compare `seen-jobs.md` rows against the index at the saved checkpoint and process only new or materially changed rows. For a changed dated file, compare each observation with its prior row signature; do not replay unchanged rows. Do not copy résumé information, contact details, full notes, or application history.
4. Normalize URLs consistently: lower-case the host, remove a leading `www`, use HTTPS, drop a trailing slash and common tracking parameters. Treat an exact normalized URL as one vacancy with **all** reporting agents and claims. Keep different URLs separate unless a human has verified that they are the same posting. Keep general careers pages marked as uncertain and distinguish closed/expired claims from open claims.
5. Compare each normalized individual vacancy URL with the cumulative `vacancies.csv` **before** adding it. In this run's `New findings`, list only URLs absent from the prior cumulative snapshot, organized by country. Put previously recorded URLs with new source observations under `Previously listed — rechecked or changed`, separate from new jobs. Put conflicting claims in a separate section and retain both. Never present unchanged historical rows as new.
6. Create a **new folder for every requested merge** at `merges/YYYY-MM-DD-NN/`, where `NN` is 01, 02, etc. for multiple requests on the same Amsterdam calendar date. Its `findings.md` holds that run's new findings, rechecks, and disagreements, each labeled and grouped by country where applicable. Its `README.md` records the run date, source commit range for each of the four repositories, counts, and any unavailable sources. Add the run to `merges/README.md`; set `latest.md` to the same run's findings. A zero-new-jobs run still gets a folder and states zero. Do not silently reuse a folder.
7. Append the new source observations to `state/observations.csv`; update `vacancies.csv` without deleting historical links, then regenerate `all-findings.md` from the cumulative CSV grouped by country. Keep search and general careers pages in `review-links.csv`. Update `conflicts.md` with substantive disagreements, retaining both claims and links to source findings. The old `updates/2026-09-29.md` remains as a historical baseline; new requested runs use `merges/`.
8. Only after the new files are published and checked, replace the four SHAs in `state/source-checkpoints.json` with the source HEADs and set `merged_at` to the run date. If a source is unavailable, leave its SHA unchanged and state clearly that it was not merged. This makes retries safe.

The date in a source file is not proof that a vacancy remains open. No fresh vacancy research is required for this merge. This is an on-request process; do not create a scheduled workflow.
